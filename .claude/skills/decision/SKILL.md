# 설계 결정 기록

주제: `$ARGUMENTS`

## 1. 대상 파일 정하기

| 주제 | 파일 |
| --- | --- |
| 수집 앱, pod 구성, HA | `plan/ingestion/plan.md` |
| 토픽, 키, 파티션, envelope | `plan/topic/plan.md` |
| Flink 등 소비자 | `plan/consumer/` (없으면 `plan.md`를 새로 만든다) |
| 서빙 | `servingapp/plan.md` |

대상 파일을 먼저 읽고 기존 고려 사항 번호와 문체를 확인한다.

## 2. 형식

기존 plan 문서와 같은 형식으로 쓴다.

```markdown
## [고려 사항 N. <주제>]

> <한 문장 질문>

- **선택 옵션**

    a. **<옵션>** ⇒ <장점> / <단점>

    b. **<옵션>** ⇒ <장점> / <단점>

- **선택 : <a|b|...>**

    - <이유 1: 이 프로젝트의 수치나 조건에 근거>
    - <이유 2>

- **감수하는 trade-off**
    - <약점과 대응 방법>
```

## 3. 규칙

- 선택이 아직 안 정해졌으면 "선택"을 비워 두고, 옵션 비교와 판단 기준만 쓴다. 대신 결정하지 않는다.
- **이유는 상대 옵션의 단점이 아니라 선택한 옵션의 장점으로 쓴다.** 상대 옵션에도 같은 장점이 있으면 그건 이유가 아니다.
- 가능하면 수치를 넣는다 (초당 메시지 수, 지연 ms, 메모리 MB).
- 약점은 숨기지 않고 trade-off에 적는다.
- 새 결정이 다른 문서(README의 "주요 설계 결정" 표, 다른 plan)와 어긋나면 고치기 전에 사용자에게 알린다.
